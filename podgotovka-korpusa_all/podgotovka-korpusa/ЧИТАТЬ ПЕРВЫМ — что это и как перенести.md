# Подготовка корпуса: что в пакете и как перенести

Папка самодостаточна. Копируется целиком, настраивается двумя файлами,
работает на чистой машине с Python.

---

## Что это

Инструмент, который превращает папку документов Word в файл фрагментов для
векторной базы: распознаёт скриншоты интерфейса, режет по структуре документа,
закрепляет номера, вычищает персональные данные и проверяет результат.

Вырос из рабочего конвейера проекта «База знаний 1С». Через него прошли **169
документов, 2 478 фрагментов, 362 распознанных экрана** — поэтому правила в нём
не придуманы, а выведены из поломок, и у каждой есть цена в числах.

Устройство и все правила — в `SKILL.md`. Это главный документ пакета.

---

## Что внутри

| | |
|---|---|
| `SKILL.md` | **читать вторым.** Устройство, шесть этапов, семь правил |
| `prepare_corpus.py` | единственная точка входа |
| `pipeline/corpusprep/` | восемь модулей: разбор docx, распознавание, нарезка, проверки, ПДн |
| `config/корпус.yaml.образец` | шаблон настроек с местами под пути |
| `config/ключи.env.образец` | шаблон файла с ключом |
| `tests/run_regression.py` | регрессия: сравнение с эталоном побайтно |
| `docs/ТЗ — подготовка корпуса.md` | задача целиком, можно передать не пересказывая |
| `docs/n8n — встраивание во флоу.md` | вызов из n8n узлом Execute Command |
| `sravnit_dokumenty.py` | отдельный инструмент: одно это или разное, что новее |
| `.gitignore` | на случай, если положите пакет под версии: закрывает ключ, рабочие данные и эталоны |

## Перенос: четыре шага

**1. Скопировать папку.** Целиком, куда угодно. Если хотите, чтобы инструмент
мог вызывать Claude Code, — положите её в `.claude/skills/` проекта или в
`~/.claude/skills/`. Для запуска руками место не важно.

**2. Поставить зависимости.**

```bash
pip install python-docx requests
```

Всё. Других нет: YAML разбирается своими силами, растеризация векторных экранов
идёт через PowerShell, который уже есть в Windows.

**3. Завести конфиг корпуса.** Скопировать `config/корпус.yaml.образец` в
`config/<имя>.yaml` и прописать три пути: откуда брать документы, куда класть
рабочие данные, куда положить готовый файл.

**4. Завести ключ.** Скопировать `config/ключи.env.образец` в
`config/ключи.env` и вписать значение.

Проверка, что всё встало:

```bash
python prepare_corpus.py --config config/<имя>.yaml --json
```

## Чего в пакете намеренно НЕТ

### Ключей

В `config/` лежит только образец с пустым значением. **Ключ не переносится
никогда** — ни в папке, ни в истории git. На новой машине он заводится заново.

### Рабочих данных

Папка `work/` с разобранными экранами, реестром и таблицей номеров **не
копируется**, и это не экономия места.

Там лежат три вещи, которые к новой машине отношения не имеют: разборы чужих
документов, **закреплённые номера чужого корпуса** и файл
`meta/на-подтверждение.csv` с настоящими ФИО и телефонами, найденными в
документах.

Номера — самое опасное из трёх. Таблица `docids.csv` закрепляет «этот документ
= DOC-20» навсегда. Принесённая в новый проект, она либо раздаст новым
документам чужие номера, либо начнёт нумерацию с середины.

**Если переносите тот же самый корпус на другую машину** — тогда `work/`
копировать нужно, целиком, вместе с номерами и кэшем распознавания. Это другой
случай: не новый проект, а переезд. Кэш экономит деньги, номера экономят
целостность.

### Эталонных документов для регрессии

`tests/run_regression.py` в пакете есть, а `tests/fixtures/` — нет: это были
настоящие документы компании, часть из них со скриншотами, где напечатаны ФИО
сотрудников.

**Как завести свои.** Выбрать пять документов, пройти их конвейером один раз,
глазами проверить результат и положить его рядом эталоном:

```
tests/fixtures/source/     пять ваших .docx
tests/fixtures/ocr/        их разобранные экраны (возьмутся из work/ после прогона)
tests/fixtures/meta/       реестр, номера, словарь сокращений, шаблон экрана
tests/fixtures/expected_chunks.jsonl    проверенный глазами результат
```

Пять штук — не случайное число: нужны документ с таблицами, документ со
схемой в векторном формате, документ с длинными нумерованными шагами, короткий
документ и документ, где в тексте есть телефон или пароль. Каждый из этих
случаев однажды ломался отдельно.

## Что настроено под наш корпус и требует пересчёта

Инструмент переносится целиком, а вот **числа — нет**. Эти настройки посчитаны
на наших документах, и на чужих будут значить другое:

| что | у нас | откуда число |
|---|---|---|
| ориентир нарезки | 1200 знаков | медиана осмысленного куска инструкции |
| верхняя граница | 2500 | дальше фрагмент перестаёт быть про одно |
| потолок прогона | 300 000 токенов | самый дорогой наш прогон стоил 316 745 |
| ожидание документов | `expect_from`/`expect_to` | просто счёт файлов в папке |

Отдельно: **порог близости поиска считается не здесь**, но пересчитывать его
придётся. У нас фрагменты журналов изменений оказались вдвое короче
инструкций — медиана 352 знака против полутора тысяч, — и порог, подобранный на
длинных текстах, на коротких перестал работать.

---

## Главное правило, ради которого всё это написано

**Измеримо то, что уже автоматизировано, а дорого то, что ещё нет.**

Шаг без журнала выглядит дешёвым потому, что данных о нём не существует. Это
правило в проекте повторилось трижды, и каждый раз сначала считали не то.
