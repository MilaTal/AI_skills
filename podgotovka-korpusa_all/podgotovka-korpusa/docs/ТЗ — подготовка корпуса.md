# ТЗ: подготовка корпуса документов к загрузке в векторную базу

Документ самодостаточный: его можно передать, не пересказывая контекст.

## 1. Задача

На входе — папка с инструкциями в формате Word. На выходе — файл `chunks.jsonl`,
где каждая строка это один фрагмент текста с семнадцатью полями метаданных,
готовый к загрузке в Pinecone.

Смысл работы не в конвертации формата. Инструкции по 1С:ДО устроены так, что
интерфейс существует только на скриншотах: текст говорит «в открывшейся карточке
документа», а названия вкладок, кнопок и полей нарисованы на картинке. Без
распознавания экранов база отвечать на вопрос «что нажать» не может. Замер по
корпусу ДО: 77 тысяч знаков текста против 235 экранов, и после распознавания
объём вырос до 280 тысяч — это и есть то содержание, ради которого всё делается.

## 2. Вход

Папка с файлами `.docx`. Прочие форматы пропускаются и попадают в отчёт.

Конфиг `config/<система>.yaml` со всеми настройками. Путей в коде нет.

Ключ доступа к модели распознавания — в переменной окружения, имя задаётся
конфигом (`recognizer.api_key_env`).

## 3. Выход

`chunks.jsonl` — по объекту JSON на строку, UTF-8 без BOM, перевод строки LF,
без отступов, без пустых строк, без запятых между строками.

Семнадцать полей, все обязательные, кроме `doc_subtype` и `screen_years`:

| поле | что кладём |
|---|---|
| `chunk_id` | 16 знаков хеша от имени файла и номера фрагмента; устойчив |
| `chunk_text` | текст фрагмента вместе с распознанными экранами |
| `source_id` | `DOC-NN`, из таблицы соответствия или по алфавиту от `start_doc` |
| `title` | короткое название документа, ориентир — имя файла |
| `document_type` | тип, по умолчанию «Инструкция» |
| `topic` | тема или подсистема, из реестра или файла тем |
| `version` | дата документа |
| `status` | «актуален» или «устарел», третьего значения нет |
| `source_url` | ссылка на папку с исходными документами |
| `updated_at` | дата обновления |
| `backup_url` | та же ссылка, если резервной копии нет |
| `section` | «название документа → заголовок раздела» |
| `doc_subtype` | подтип, если уместен |
| `system` | `DO` или `ERP` |
| `source_file` | имя исходного файла |
| `screen_years` | годы, видимые на скриншотах |
| `has_screen` | есть ли в этом фрагменте разбор экрана |

Дополнительно: файл сокращений вне словаря — две колонки, сокращение и где
встретилось. Расшифровки не выдумываются, их подтверждает владелец процесса.

## 4. Правила нарезки

Резать по структуре документа, а не по числу знаков. Ориентир 1200 знаков,
верхняя граница 2500.

Не разрывать: распознанный экран, таблицу вместе с подписью, абзац с двоеточием
вместе со следующим списком, нумерованные шаги процедуры, абзац с отрицанием
вместе с продолжением.

Про отрицания стоит помнить довод: порванная таблица видна глазом сразу, а
оборванное «не поддерживает» выглядит как уверенный правильный ответ.

Если неделимая единица не влезает в предел, она режется по внутренним границам —
между строками таблицы с повтором шапки, между элементами перечня, по точкам, в
последнюю очередь по запятым. Одной границы недостаточно: перечень кодов операций
на 11 тысяч знаков делится только по запятым.

## 5. Правила по данным

**Телефоны и пароли не попадают в базу ни в каком виде.** На месте изъятого
ставится отметка `ХХХ`. Вычистка применяется к тексту документа, к распознанному
экрану и к ячейкам таблиц — пароль просачивался через все три.

**Персональные данные обезличиваются.** ФИО заменяется на «Иванов И.И.» в любом
виде: полностью, инициалами, в строке автора. Служебные почтовые ящики и названия
организаций остаются — они часть инструкции.

**Названия элементов интерфейса переносятся дословно.** Пользователь спрашивает
теми словами, которые видит на кнопке, и пересказ здесь равен потере.

**Ничего не додумывается.** Если элемент не читается, так и пишется. Если в
инструкции чего-то нет — значит нет, и бот честно откажет.

## 6. Проверки перед выпуском

Каждая строка разбирается как JSON. Во всех строках семнадцать полей. `system`
одинаков во всех строках. Нет заглушек и пустых обязательных полей. Нумерация без
пропусков и пересечений. Нет дублей `chunk_id`. Нет персональных данных,
телефонов и паролей. Нет следов залипания модели — сорока одинаковых символов
подряд.

Отдельно и обязательно: открыть три фрагмента наугад и прочитать. Понятно ли, о
чём речь, не оборван ли шаг посередине. Этот пункт важнее остальных: был случай,
когда прогон отрапортовал об успехе, а база оказалась разрушена, и заметили это
только по содержанию.

## 7. Коды возврата

`0` — собрано и проверено. `1` — собрано, но проверка нашла замечания. `2` —
ошибка входа: нет конфига, папки или ключа. `3` — не удалось распознать экраны.

## 8. Чего делать не надо

Не пересоздавать существующие `source_id`: они стоят в реестре, в журнале
обращений и в отчётных документах.

Не смешивать корпуса разных систем в одном файле.

Не дописывать содержание «для полноты». Пользователь выполнит процедуру, которой
не существует.

Не расшифровывать сокращения самостоятельно. Из семи проверенных «неизвестных
сокращений» шесть оказались ошибками распознавания коротких слов, а не новыми
терминами: «Начальник ОЭ» вместо «ОЗ», «Направить ДД» вместо «ГД».

## 9. Регрессия

Перед каждой правкой правил нарезки или вычистки прогонять
`python tests/run_regression.py`. Набор — пять реальных документов корпуса,
включая один без экранов и один с телефонами в подписи. Тест проверен на
чувствительность: он ловит изменение целевого размера фрагмента, верхнего
предела, отметки вычистки, правила телефонов, границ блоков и признака экрана.
